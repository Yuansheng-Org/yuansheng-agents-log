# Diagnosis

Software: onednn
Testcase: eltwise\_f16\_upstream
Function: jit\_uni\_kernel.2
Verdict: `confirmed`

Summary: In the JIT-emitted RVV eltwise kernel jit\_uni\_kernel.2, the rv64 eltwise JIT injector re-materializes ~25 loop-invariant f32 constants inside the hot loop on every iteration (lui+addiw+fmv.w.x and li sequences at 0xa4-0x29c), which is ~70 of ~135 loop instructions (~52%); the emitter's load\_f32\_const places li+fmv\_w\_x at each use site instead of hoisting constants before the loop or loading them from a constant table, and this redundant per-iteration materialization is the dominant instruction-issue cost of the measured hotspot.

## Findings
- `confirmed` (root cause, high) In the JIT-emitted RVV eltwise kernel jit\_uni\_kernel.2, the rv64 eltwise JIT injector re-materializes ~25 loop-invariant f32 constants inside the hot loop on every iteration (lui+addiw+fmv.w.x and li sequences at 0xa4-0x29c), which is ~70 of ~135 loop instructions (~52%); the emitter's load\_f32\_const places li+fmv\_w\_x at each use site instead of hoisting constants before the loop or loading them from a constant table, and this redundant per-iteration materialization is the dominant instruction-issue cost of the measured hotspot.
  Reasoning: Disassembly of jit\_uni\_kernel.2 shows the hot loop body 0x8c-0x2c0 contains ~27 lui + ~18 addiw + ~25 fmv.w.x + 2 li sequences re-materializing the identical f32 constants (MINLOGF/MAXLOGF/log2e/C1/C2/exp-poly and erf-poly coefficients, mask 0x7fffffff, shift 126/23) on every iteration. The source load\_f32\_const (jit\_uni\_eltwise\_injector.cpp:81) emits li+fmv\_w\_x at each use site inside the loop, and exp/erf/log paths call it per constant. Constant setup is ~70 of ~135 loop instructions (~52%), with hotspot lines spread across both constant loads and RVV ops; IPC 0.679 and low cache/branch miss rates indicate an issue-bound compute loop. Hoisting constants out of the loop or loading them from a constant pool would remove roughly half the loop instructions.
- `probable` (contributing factor, medium) With VLEN=128 and f16 lanes (pointer advance slli t1,t0,1 in the loop tail), each iteration of jit\_uni\_kernel.2 processes at most 8 f16 elements at LMUL=1, so the fixed per-iteration cost (vsetvli, pointer updates, back branch, and all constant setup) is amortized over very few elements (~135 instructions per 8-element chunk); raising LMUL to m2/m4 would amortize the same fixed loop cost over 16/32 lanes per iteration, subject to the spill-free register budget.
  Reasoning: Metadata fixes VLEN=128 on C920v2; the loop advances pointers by t0\*2 bytes (slli t1,t0,1) so each iteration processes t0 f16 elements, at most 8 with LMUL=1. The loop body is ~135 instructions for 8 elements (~17 instructions/element), a very high per-element cost that includes vsetvli (0x90), pointer updates, the back branch, and all constant setup. Raising LMUL to m2/m4 would amortize the fixed per-iteration vsetvli/pointer/branch cost over 16/32 lanes, but the LMUL is inferred (vsetvli opcode is not decoded by this objdump), so this is a contributing factor with medium confidence.
- `false_alarm` (false alarm, high) The \`.insn 4, 0x...\` entries throughout jit\_uni\_kernel.2 are undecodable-by-this-objdump RVV instructions emitted by the Xbyak\_riscv JIT backend, not corrupted or miscompiled code; they should not be treated as evidence of a codegen bug.
  Reasoning: The entire rv64 backend emits raw RVV encodings via Xbyak\_riscv (cpu\_isa\_traits.hpp: XBYAK\_RISCV\_V=1), and the disassembler in the perf environment renders them as \`.insn 4, 0x...\`. The injector source confirms the intended sequence (vsetvli, vle/vse, vf-form FMA/mul/add, vmerge) matches the observed constant pattern, so the \`.insn\` lines are a tooling artifact, not a defect.

## Gaps
- `baseline_gap_measurement`: The perf annotate disassembly renders all RVV instructions as raw \`.insn 4, 0x...\` because the toolchain objdump lacks RVV decode support, so SEW/LMUL, exact FMA vs add/mul opcodes, and widening structure in the loop body are inferred from source and VLEN rather than directly observed.
- `implementation_shape_gap_actionability`: The perf stat is whole-workload (62.7T cycles, 42.6T instructions) while the annotate is local to jit\_uni\_kernel.2, so the kernel's exact share of the workload and the achievable speedup bound from hoisting the ~60-70 loop instructions are estimates, not measured shares.
- `source_context_gap_analysis`: The exp/erf/log path of the rv64 eltwise injector was read from source, but the host kernel that calls the injector and the loop-generation point (where a prologue for constant hoisting would be inserted) was not located; the source on demand only surfaced the injector.
- `source_context_gap_missing_source`: Local source evidence is unavailable at src/cpu/riscv64.
- `source_context_gap_missing_source`: Local source evidence is unavailable at src/cpu/rv64/xbyak.
- `source_context_gap_missing_source`: Local source evidence is unavailable at src/cpu/riscv64.

## Actions
- `conditional`: In the rv64 eltwise JIT injector (src/cpu/rv64/injectors/jit\_uni\_eltwise\_injector.cpp), change the constant-emission contract so the ~25 loop-invariant f32 constants (MINLOGF, MAXLOGF, log2e, C1, C2, exp-poly p0..p5, erf/erf-related coefficients, 0.5/1.0/2.0, mask 0x7fffffff, shifts 126/23) are hoisted out of the per-iteration loop body: materialize each constant once in a loop prologue into dedicated FP scalar registers (or load once from a small rodata constant table) and have the in-loop vf-form ops reference those pre-loaded registers instead of calling load\_f32\_const at each use site. This requires the injector to expose a hoist/prologue step or to split constant setup from per-element compute so the emitter does not re-emit li+fmv\_w\_x per iteration.
- `conditional`: After (or independently of) hoisting loop-invariant constants, evaluate raising the RVV LMUL of the eltwise compute from m1 to m2/m4 in the rv64 JIT kernel so each iteration processes 16/32 f16 lanes on VLEN=128, amortizing the fixed per-iteration vsetvli, pointer update, and branch cost over more elements. Select only spill-free candidates that satisfy LMUL\*peak\_live\_vectors\<=32 with legal f16-\>f32 widening EMUL, and retain strip-mined tails.
