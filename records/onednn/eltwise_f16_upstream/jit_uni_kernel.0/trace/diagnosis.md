# Diagnosis

Software: onednn
Testcase: eltwise\_f16\_upstream
Function: jit\_uni\_kernel.0
Verdict: `confirmed`

Summary: The oneDNN RISC-V JIT emitter rematerializes the same set of ~15 single-precision activation coefficients inside the hot eltwise\_f16 loop body on every iteration instead of hoisting them out of the loop, adding ~30 scalar lui/addiw/fmv.w.x instructions per iteration that dominate the hot interval (lui hotspots at 0x18c 9.68%, 0xa0/0xc4/0x138/0x160/0x174/0x1ac 6.45% each, plus ~15 lines at 3.23%); the loop is compute/issue-bound, not memory- or branch-bound (L1 miss 0.328%, branch miss 0.360%, IPC 0.679).

## Findings
- `confirmed` (root cause, high) The oneDNN RISC-V JIT emitter rematerializes the same set of ~15 single-precision activation coefficients inside the hot eltwise\_f16 loop body on every iteration instead of hoisting them out of the loop, adding ~30 scalar lui/addiw/fmv.w.x instructions per iteration that dominate the hot interval (lui hotspots at 0x18c 9.68%, 0xa0/0xc4/0x138/0x160/0x174/0x1ac 6.45% each, plus ~15 lines at 3.23%); the loop is compute/issue-bound, not memory- or branch-bound (L1 miss 0.328%, branch miss 0.360%, IPC 0.679).
  Reasoning: Provenance is directly JIT-generated code (jit\_uni\_kernel.0 in jitted-12109-0.so). Annotate shows 15 lui+addiw+fmv.w.x constant-materialization sites whose aggregate sample share is ~58% of the function's hotspot samples, all inside the single loop interval (0x8c backedge 0x1d4). The coefficients (0x3f800000, 0x3f000000, 0x40000000, 0x42b17218, 0xc2aeac50, 0x3fb8aa3b, 0x3f318... through 0x3e2aaaaa) are loop-invariant FP polynomial/FMA coefficients for a softplus/exp-family activation and never change across iterations. The emitter fails to recognize them as loop-invariant (JIT-quality 'redundant constant loads in generated sequences'). Bound type: instructions-per-cycle 0.679 with near-zero cache and branch miss rates indicates issue-bandwidth/dependency-bound execution where removing scalar materialization directly lowers dynamic instruction count.
- `probable` (contributing factor, medium) The JIT-emitted loop re-executes the vsetvli-style vector-state setup at 0x9c on every iteration (backedge 0x1d4 -\> 0x8c) even though vl and vtype are loop-invariant with no intervening call, inline asm, or state clobber, adding a redundant vector-configuration instruction to the fixed-VL main loop body.
  Reasoning: The function is a fixed-VL main loop: pointer advances by slli t1,t0,1 (element\*2), a4-=t0, unconditional backedge j 0x8c; the vsetvli-style instruction at 0x9c (encoding 0x0d12f057, vsetvli rd,rs1,vtype class) re-executes each iteration with no state-modifying instruction in between. rvv\_vector\_state\_management's profile signal is 'repeated vsetvli in a hot vector loop with no intervening instruction that changes vl/vtype', met here; route confidence Medium because the emitter's invalidation point is inferred from the emitted loop rather than direct emitter source, and the instruction is a single per-iteration cost subsumed by the JIT-quality root cause.
- `false_alarm` (false alarm, high) The rvv\_elementwise\_activation\_kernels pattern does not match this hotspot: the eltwise\_f16 softplus/exp activation is already fully RVV-vectorized with no scalar branches/selects, parameter broadcasts, math-helper calls, or range reduction dominating; the hot samples are in already-vectorized vfwmacc/vfmadd/vse-style code and the scalar lui materialization, not in an unvectorized activation path.
  Reasoning: The row's positive signals (scalar branch/select or exp/tanh helper dominating) are absent: the annotated loop body is an RVV FMA chain (encodings 0xe0..0x1b8 are vfwmacc/vfmadd/vse family) with the only scalar overhead being coefficient materialization, which belongs to the JIT-quality finding. The kernel is already the vector-math form the pattern would prescribe; no unvectorized activation body exists to fix.
- `false_alarm` (false alarm, high) The rvv\_precision\_conversion\_kernels pattern does not match: the f16-\>f32 widening for eltwise\_f16 is already performed with RVV widening instructions (vfwmacc/vfwadd-style encodings at 0xe0/0xe4 and halfword-scaled loads at 0x90), with no scalar conversion helper, per-element special-value branching, or pack/unpack emulation dominating samples; conversion is a sub-step of an activation whose samples are dominated by the FMA chain and constant materialization.
  Reasoning: The row applies only when conversion work itself dominates samples; here no conversion instruction or helper address shows a meaningful share, the pattern explicitly states that when an activation dominates, the operator pattern owns it, and the conversion is already a vector widening with correct vtype setup. No conversion-specific hotspot exists to repair.

## Gaps
- `evidence_gap_confidence`: baseline\_gap: sampling IP precision. precise\_ip / Exact-IP / PMU skid for the sampled cpu-clock event is not provided, so single-line percentages (e.g., 9.68% at 0x18c) can only be treated as loop-interval anchors, not instruction-latency attribution.
- `baseline_gap_measurement`: baseline\_gap: build ISA for the JIT blob. Tag\_RISCV\_arch is only captured for benchdnn ELF binaries, not for the runtime-generated jitted-12109-0.so containing jit\_uni\_kernel.0; the emitted RVV encodings are consistent with an RVV 1.0 + Zvfh build but the object-level attribute is unconfirmed.
- `source_context_gap_analysis`: source\_context\_gap: the oneDNN RISC-V JIT emitter source was not inspected; the JIT-quality and vector-state conclusions are derived from the emitted-kernel annotate and the knowledge that the function is JIT-generated, without direct confirmation of the emitter's loop-invariant and vector-state handling.
- `baseline_gap_measurement`: evidence\_gap: cache counters appear scaled/unreliable (cache\_references 3,967,258 and cache\_misses 3,968,051 against 42.5T instructions yield a 100.020% 'miss rate' artifact), so memory-bound determination is only approximate; the compute/issue-bound interpretation rests on L1 0.328% and branch 0.360% rates being sane.
- `source_context_gap_missing_source`: Local source evidence is unavailable at src/cpu/riscv64.

## Actions
- `conditional`: In oneDNN's RISC-V CPU JIT emitter, make the elementwise-activation generator recognize the vector-math FP coefficients as loop-invariant and hoist their lui+addiw+fmv.w.x materialization out of the fixed-VL main loop (materialize once before the loop into FP/vector registers that are live across the backedge), instead of re-emitting the ~15 constant sites on every iteration.
- `conditional`: Make the oneDNN RISC-V JIT emitter's vector-state tracking survive loop backedge emission for fixed-VL main loops: emit vsetvli once before the loop when vl/vtype are proven compatible, and skip the redundant per-iteration setup (0x9c) rather than invalidating state at every branch/label (the rvv\_vector\_state\_management invalidation-point rule).
